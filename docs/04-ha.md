# 撮合引擎主备热备（active–hot standby）设计 — 调研与验证（2026-09-01）

> **本章解决**：主机宕机后如何由备机接管、主备如何保持状态一致。
> **前置依赖**：01、03（撮合确定性是主备一致的前提）。
> **读者前置**：复制 / 仲裁 / fencing。

> 迁移自 open-cex-docs `design-docs/20-match-engine-ha.md`（2026-09-05 迁入 open-cex-match/docs）。



## 1. 目标与语义

生产形态从"单实例"升级为**主备热备**：

- **主实例（primary）**：正常收单 → 撮合 → 成交/深度写 Archive → 下游冷读。即现有完整形态。
- **备实例（standby）**：与主机消费**同一输入序列**，用同一确定性撮合逻辑陪跑，
  内存订单簿保持与主机一致；**不对外输出成交**（egress/Archive 只落本地影子盘，下游不消费）。
- **接管**：主机故障后，外部协调者裁决提升备机；备机补齐分裂窗口后立即对外输出
  成交，下游消费源切到备机 Archive。

引擎侧核心前提（已具备）：撮合确定性 —— 单 symbol 单线程、同一输入序列必得同一
状态（05 文档 §1.1）。因此热备不需要复制"状态"，只需要保证**输入序列一致**。

## 2. Aeron 官方 HA 能力调研（2026-09-01）

### 2.1 三层能力

| 层 | 能力 | 开源 | 我们现状 |
| --- | --- | --- | --- |
| 传输层 | multicast / MDC 多路分发；Archive replication（recording 复制） | ✅ | 已用 Aeron 传输 + Archive；**replication 通道已配置未启用**（`OcxArchiveMain` replicationChannel localhost:8011） |
| Aeron Cluster | Raft 共识：日志复制 + 自动选主 + 快照重建 | ✅ | 未采用（01-architecture.md §1.5 边界）；引擎需重写为 ClusteredService |
| Cluster Standby | 专门的热备组件（standby 拉日志驱动本地服务，TransitionModule 转正） | ❌ Premium | 不可用：商业授权 + 依赖 Cluster 主集群 |

### 2.2 三个关键 Aeron 约束

1. **多 session 无总序**（官方 Channels/Streams/Sessions 文档）：同一 channel+stream
   多个 publication 各自 sessionId，顺序只在单 Image 内保证。单实例撮合"无碍"，
   但热备**有碍**：主备若各自由多 session 聚合出不同交错顺序，状态会悄悄分叉。
   → 热备输入必须收敛为**单一 session 序列**。
2. **多播流控**：multicast 默认 `fc=max`，慢接收者直接丢数据且无法 NAK；`fc=min`
   以最慢者约束 sender（备机拖慢主机）；接收者超时（默认 2s）会被踢出流控组。
   → 多播扇出不是免费的，掉队备机只能靠 Archive 补齐。
3. **Aeron Cluster 2 节点不自动**：官方文档明确 2 节点集群需两成员都同意日志，
   故障后剩余成员必须**手动**重配置为单节点才能继续；自动接管需要 3 节点。

## 3. 方案（路线 A：确定性双实例 + Archive replication）

### 3.1 拓扑

```
网关（单 session 发号/转发）
  │  Aeron UDP 收单（现有 ingress 端点）
  ▼
┌──────────────────────── 主实例（机 A） ────────────────────────┐
│ media-driver ─ ingress ─ core ─ egress ─ Archive（真实输出）    │
└────────────────────────────────────────────────────────────────┘
        ▲                                  │  Archive replication
        │  （备机输入序列 = 主机入站 recording）  ▼
┌──────────────────────── 备实例（机 B） ────────────────────────┐
│ media-driver ─ ingress(可选) ─ core ─ egress(静默) ─ Archive    │
└────────────────────────────────────────────────────────────────┘
        ▲
        └── 协调者（探活 / 裁决 / 提升指令，走 Aeron 控制流扩展）
```

### 3.2 输入一致性（本方案核心）

备机的输入序列 = **主机 Archive 的入站 recording 复制流**，而非直接收网络：

- 主机 Archive 持续记录入站流（现状即如此，崩溃恢复唯一事实来源）；
- 备机 Archive 用 `replicate(recordingId, NULL, ...)` 实时复制该 recording，
  复制位置即备机输入位置；
- 备机 core 消费**复制后的 recording**（回放/实时订阅）重跑撮合 → 状态与主机
  逐字节一致（确定性保证）；
- 单 session 问题自然消解：主机录制序列 = 主机实际应用序列 = 备机应用序列。

选此路线而非"多播双发"的理由：

| 方案 | 优点 | 缺点 |
| --- | --- | --- |
| multicast/MDC 双发 | 备机实时性最好 | 多 session 无总序风险；fc=max 丢数据 / fc=min 拖慢主机；需要上游改造 |
| 网关单 session 双发 | 序列一致、实时 | 网关必须支持双路；网络抖动时两路可能不一致 |
| **备机复制主机 recording（选定）** | 序列天然一致；复用现有 Archive/恢复设施；主机链路零改动 | 备机滞后 = 复制延迟（本机验证 <200ms）；主机 Archive 是单点（故障瞬间未复制帧需定义语义） |

### 3.3 备机形态

- 备机跑完整五进程（或精简：ingress 可省，直接由复制端向 core 入站环喂帧）；
- egress 静默：不向任何下游发布成交/深度，或发布到备机本地 Archive（影子盘，
  供自身恢复与对账，下游不消费）；
- 备机快照照常（接管时自身恢复能力完整）。

### 3.4 分裂窗口与接管

切换瞬间主备不可能严格同拍，窗口内帧存在三种归属：

1. 主机已录制且备机已复制 → 安全（备机已应用）；
2. 主机已录制但备机未复制 → **补齐**：提升前备机继续复制追平（RTO 增加复制
   剩余延迟）；或由协调者等待"复制位置 ≥ 主机确认位置"（同步语义）；
3. 主机已接收但未录制（recorder 落后窗口）→ 与崩溃恢复同语义：快照 + 回放兜底
   （06-crash-recovery.md §1.2  崩溃窗口），备机接管后由下游对账处理。

接管协议（外部协调者，引擎不选主）：

```text
协调者 ──探活（心跳）──▶ 主/备
主机超时（N×心跳周期）→ 协调者发 PROMOTE 到备机
备机：停复制 → 追平到主机最后录制位置（或容忍定义缺口）→ 开启真实输出
→ 通知下游切换消费源（备机 Archive）
```

控制面复用 `ControlStream`（现有 READY/GO，20B 定长行），扩展类型：
HEARTBEAT / ROLE / PROMOTE / DEMOTE。

### 3.5 一致性对账（防静默漂移）

主备各自确定性重放，理论上状态一致；但 bug/配置偏差会导致静默分叉。周期性轻量
对账（在线版，非离线重放）：

- 成交计数、在簿/条件单计数、快照哈希（可在快照帧里加状态摘要）；
- 主备各上报，协调者比对；不一致 → 事件告警 + 禁止提升。

## 4. 技术验证（已完成，2026-09-01）

`ocx-match-egress/src/test/java/com/ocx/egress/ArchiveReplicationTest.java`：
主 Archive 录制 200,000 帧入站行（264B 定长行，recording 320B/行 → 64MB）→
备 Archive `replicate`（stopPosition=NULL 实时追）→ 停源后校验：

| 项 | 结果 |
| --- | --- |
| 复制追平耗时 | **172ms**（含复制建立 + 64MB 传输） |
| stopPosition 一致 | 64,000,000 == 64,000,000 ✅ |
| 字节数一致 | startPosition/stopPosition 差完全一致 ✅ |
| 复制过程 | live 位置 1.2MB → 15MB → 42MB → 64MB 单调追进 |

结论：Archive replication 本机实时复制可行、字节精确、滞后亚秒级。

### 5.4 fencing / 防双主（2026-09-01）

**问题**：协调者靠心跳超时判定主机死亡，但心跳超时 ≠ 主机真死（网络分区/抖动）。
若协调者误判并提升备机，主机若还活着继续输出即成双主。

**四层防护**：

1. **租约（Lease）**：主机心跳 = 续租；协调者维护租约，过期才允许提升
   （HA 控制流扩展 LEASE_ACK，主/备各自的 ACK 通道可配置，同机实验错开端口）；
2. **Epoch / fencing token**：协调者维护递增 epoch，每次提升 epoch++ 并随 PROMOTE
   下发；所有 LEASE_ACK 携带当前 epoch；
3. **Self-fencing（fail-stop）**：`HaHeartbeat` 检测到——
   - primary 收到的 ACK epoch 变化（被取代）→ 立即自杀（停撮合线程）；
   - 连续 3 次无 ACK（协调者失联/分区）→ primary 自杀；
   网络分区时宁可停机，绝不双主（1+1 无多数派，必须 fail-stop）。
   standby 被提升（epoch 变化）→ **接受新 epoch 继续**（不得误自杀）；
4. **输出侧 fencing（天然）**：出站 cold-log，下游只读 active 实例 Archive；
   切换后旧主机 Archive 被忽略，僵尸输出进不了下游。

**实现**：`HaControlStream.TYPE_LEASE_ACK`（position 字段携带 epoch）、
`HaHeartbeat` 请求-确认循环 + fence 回调、`HaCoordinatorMain` epoch 管理 +
按实例路由 ACK、`MatchCoreBootstrap` fence 回调停止撮合线程、
`ReplicationIngressBridge` 记录 PROMOTE 的 epoch。

**验证**：

- 集成（/tmp/perf-fencing-2）：kill 主机（STONITH）→ 协调者 epoch=2 PROMOTE →
  备机接管（trades 181,104→348,306），bridge 记录 `EPOCH=2`；
- 单测（HaHeartbeatFencingTest × 2 通过）：primary 收到吊销 epoch →
  `SELF_FENCED`（防双主）；standby 被提升（epoch 1→2）→ 不误自杀；
- fail-stop 原则固化：任何实例无法确认"自己是唯一 active"时停止输出。

**残余说明**：协调者本身是单点（挂掉则 HA 失效但不会双主）；生产若要更强，
可让协调者双实例 + 简单仲裁，或在强一致场景引入 Aeron Cluster（Raft 任期天然
防双主）。**已落地为 §5.5 仲裁层 Raft（3 节点 Ratis 组）**。

### 5.5 仲裁层 Raft——3 节点 Ratis 组（2026-09-01，feature/raft-arbitration）

**动机**：§5.4 的协调者（HaCoordinatorMain）是单点：它挂掉时 HA 失效（心跳无人
确认、提升无人裁决）。虽然 fail-stop 保证不会双主，但"协调者可用性"成为系统
可用性的短板。引入 3 节点 Ratis 仲裁组后，协调决策（谁 active / epoch / 租约）
由多数派共识承载，容忍 1 个仲裁节点故障。

**架构**：撮合路径不变（主备 + Archive 复制 + bridge + cold-log 出站），Ratis
组只仲裁"元状态"，不复制撮合日志。引擎侧 UDP 面不变——core 仍发
`TYPE_HEARTBEAT`，仲裁节点回 `TYPE_LEASE_ACK`（position=epoch），提升仍发
`TYPE_PROMOTE`（ReplicationIngressBridge 照旧消费）；区别是引擎心跳现在发给
**全部 3 个仲裁节点**（`-Docx.ha.udp.endpoints` 逗号分隔，兼容单点
`-Docx.ha.udp.endpoint`），仅 Raft leader 裁决续租/ACK/提升。

**状态机**（`HaArbitrationStateMachine`，继承 Ratis `BaseStateMachine`）：

| 字段 | 含义 |
|---|---|
| epoch | fencing token，初始 1；每次提升 +1 |
| activeInstanceId | 当前 active 实例 |
| leaseExpiryNs | 租约截止（提议方时钟域，随日志复制，三节点确定性一致） |
| members | 实例成员表（role + 复制位置，提升候选排序） |

**命令**（`HaArbitration` 手工 ByteBuffer 编码，不引 SBE）：

| 命令 | 语义 |
|---|---|
| REGISTER | 幂等注册；首个 primary 注册即初始 active（epoch=1） |
| RENEW | 仅当前 active 且 epoch 匹配才延长租约；expiry 取 max（只延长不倒退） |
| PROMOTE | 仅 `proposalTimeNs >= leaseExpiryNs`（租约在提议方时钟下已过期）才提交：epoch++、换 active、授予新租约 |
| QUERY | 只读（走 `StateMachine.query`，不进日志） |

**防双主闭环（与 §5.4 完全兼容）**：

- 提升即 epoch++，旧 primary 下一次续租（ACK）拿到新 epoch → 引擎侧
  `HaHeartbeat` 吊销检查 → self-fence（fail-stop）；
- 新 active 立刻获得新租约，同轮第二个 PROMOTE 被 `ST_LEASE_ACTIVE` 拒绝
  （防连升/双主窗口）；
- 仲裁组多数派失效（挂 2 节点）→ 无法提交 → 租约续不上 → primary fail-stop，
  宁可停机不双主。

**判活门槛**：必须先见过 active 至少一次心跳才允许判死（启动期租约初始为 0
视为过期，但没见过心跳不提升），与 HaCoordinatorMain 语义一致。

**实现**：`HaArbitration`（编码）、`HaArbitrationStateMachine`（状态机）、
`HaRaftCoordinatorMain`（3 节点 Ratis server + UDP 网关，参数
`-Docx.ha.raft.id/-Docx.ha.raft.peers/-Docx.ha.raft.storage.dir/
-Docx.ha.raft.lease-ttl-ms(默认 10s)/-Docx.ha.raft.renew-interval-ms(默认 3s)/
-Docx.ha.raft.election-timeout-min-ms(默认 300)/-max-ms(默认 700)`），
`HaHeartbeat`/`MatchCoreBootstrap` 支持多仲裁节点心跳扇出。

**依赖**：`org.apache.ratis:ratis-server/ratis-common/ratis-grpc/
ratis-metrics-default:3.3.0`（gRPC server 需显式
`GrpcConfigKeys.Server.setPort` 绑 peer 端口，默认 port=0 是随机端口）。

**验证**：

- `HaArbitrationStateMachineTest`——进程内 3 节点组：REGISTER→epoch=1/
  active=primary；RENEW 租约生效；租约内 PROMOTE 被拒；租约过期提升 epoch=2 换人；
  旧 primary 续租拿到新 epoch（吊销信号）；新 active 租约立即生效阻止同轮连升；
  三节点 apply 后状态一致。core 全量 104 测试通过（含既有 HaHeartbeatFencingTest
  ×2）。
- 端到端 `standby-test.sh --raft --failover`（/tmp/perf-raft-e2e2）：
  主备指标一致（trades/book/rejected 相等）→ kill 仲裁 leader（arb3）→ 新 leader
  当选、主机续租不中断（无 SELF_FENCED）→ kill 主机链路 → 租约过期自动提升
  （PROMOTE_SENT EPOCH=2）→ bridge STANDBY_PROMOTED → producer2 打备机 →
  备机 trades 92,052→211,131 继续增长（无回退）。
- 高频路径修复：HaHeartbeat/协调者 ACK 改常驻 publication 复用，消除
  "SendChannelEndpoint CLOSING" 瞬态异常（此前心跳线程可能静默死亡触发误提升）；
  心跳线程整体 try/catch，瞬态错误由 missed-ACK 计数兜底 fail-stop。
- **启动宽限**（HaHeartbeat）：编排/部署顺序下协调者可能晚于引擎就绪，primary
  若从启动即刻计数失联会在协调者上线前误自杀。语义：收到首个 ACK 前不累计失联
  （未确认自己是 active，无从吊销），收到首个 ACK 后立即恢复严格 fail-stop；
  另有硬宽限 `-Docx.ha.heartbeat.startup-grace-ms`（默认 30s）兜底。新增
  HaHeartbeatFencingTest ×2（宽限期内不自杀/首个 ACK 后失联快速自杀）。
- **独立仲裁媒体驱动**（aeron-arb）：仲裁组连独立 driver，不随主机/备机 kill
  受影响（此前误连主机 driver，kill 主机链路时仲裁组 Aeron client 超时崩溃）。
- **PROMOTE 多端点**：`-Docx.ha.promote.endpoints` 逗号分隔，双备机各自 bridge
  监听独立端口（备机1 53000 / 备机2 53021）收 PROMOTE，按 instance-id 过滤。
- **一主两备高压验证**（standby2-test.sh，/tmp/perf-standby2，150k TPS × 15s）：
  三实例陪跑一致（host=sb1=sb2=437,587 trades / book 60,675 / rejected 737）→
  kill 仲裁 leader 自愈（主机无 SELF_FENCED）→ kill 主机 → 租约过期自动提升
  standby=2（EPOCH=2）→ 被提升备机 trades 437,587→1,173,189（无回退），
  落选备机保持 standby（SELF_FENCED=0 不误自杀）。

**残余/后续**：

- 仲裁组 3 节点需要 NTP 对齐（时钟域交错已用 max() 保证租约只延长不倒退；
  跨域提升窗口受时钟偏差影响，生产建议 <100ms）；
- **高压复制追赶延迟**：150k TPS 且机器接近满载时，从 recording 起点回放的备机
  可能落后 ~1%（回放吞吐≈写入速率）；机器负载回落（sb-heap 2g）后三实例完全
  一致。生产上备机复制延迟与 TPS 正相关，接管会丢"未复制完成"的尾部输入，
  由客户端 correlationId + 重试兜底；
- **接管延迟语义（2026-09-01 澄清）**：从主机宕机到备机接管约 **5~7s**
  （实测 92,052→211,131 场景）。构成：心跳周期 1s 确认停跳 + 判死门槛
  `ocx.ha.primary-timeout-ms`=5s + 租约过期（RENEW 2s/次、TTL 5s，最后续租后
  最迟 5~7s）+ Raft 提升提交（亚秒）。这不是未优化，而是防双主的必要代价：
  判死必须同时满足"租约过期（共识判定的权威依据）+ 心跳超时"，避免网络抖动
  误提升。想更快可调小 TTL/超时（如 TTL 2s + 判死 1s ≈ 3s 内接管），代价是
  仲裁组写频率上升、对抖动更敏感，生产按网络环境权衡。接管时状态是热的
  （备机陪跑一致，无需回放），仅"bridge 停转发 + 备机收自己的 ingress"；
  主机宕机瞬间未复制的输入会丢，客户端 correlationId + 重试兜底。
- **P0-1 备机 position 持续上报（已落地）**：备机 core 心跳携带 standbyInbound

## 7. 故障接管实验（2026-09-01 设计）

### 7.1 阶段 A：脚本编排的最小接管

**目标**：主机进程被杀后，备机能从自身状态继续撮合并输出成交——成交记录连续、
无重复、无缺口（就备机已复制的输入而言）。

**前置差距（M1 后待补）**：

| 差距 | 补法 |
| --- | --- |
| 备机无收单端点 | 备机常驻 ingress（UDP 11001）：接管前无流量，接管后为新收单端点 |
| 备机无真实输出 | 备机 egress 替代 drain（影子输出）：写备机 Archive 成交/深度 recording，接管前下游不消费（M3 静默形态） |
| 备机 Archive 未录 trade/depth | StandbyArchiveMain 常驻 startRecording 备机 trade/depth 流（方案 A，规避运行中 startRecording 缺陷） |

**步骤**：

```text
1. 双实例陪跑（50K TPS × T1）→ 记录主机/备机 trades、在簿
2. kill 主机链路（core/ingress/egress/Archive/media，模拟整机宕机）
3. 备机复制追平剩余输入（bridge 消费完复制 recording 尾部）→ 停 bridge
4. 启动 producer2（--instance-id 2）→ 备机 ingress(11001)
5. 备机 core 继续撮合，egress 持续写备机 Archive（影子 → 真实输出）
6. 验证：
   a. 备机 trades_total 在接管点后继续增长（无跳变）
   b. 备机成交总数 = 主机已录制成交 + 新成交（无重复/无丢失）
   c. 备机 in/outbound recording 完整（复制字节与主机一致）
   d. 主备 orderId 空间不冲突（producer1/2 用 instance-id 1/2）
```

**验收标准**：接管点主备成交计数衔接无回退；备机在簿状态无回退；无幽灵单。

### 7.2 阶段 A 实验结果（2026-09-01 首跑）

`standby-test.sh --failover`（50K TPS：正常段 15s + 接管段 15s，产物
/tmp/perf-failover-1）：

| 节点 | 结果 |
| --- | --- |
| 主机宕机前 | host_trades=199,715 == standby_trades=199,715（陪跑一致） |
| 故障注入 | kill -9 主机全部 5 进程（media/archive/egress/core/ingress） |
| 备机接管 | standby_trades 199,715 → **334,800**（+135,085 笔新成交，无回退） |
| 备机在簿 | 1,568（接管后正常处理新流量，rejected=219 ≈ 0.16% 属正常拒绝） |

结论：**主机整机宕机后备机能从自身状态继续撮合并输出成交**。阶段 A 的输入切换
（producer → 备机 ingress）由脚本编排完成；阶段 B（协调者自动探活/PROMOTE）见 M2/M4。

### 7.3 阶段 B：自动接管（M2/M4 完成后）

协调者探活（心跳）→ 主机超时 → 发 PROMOTE → 备机自动停 bridge、
确认复制追平、切换输出 → 通知下游切消费源。自动化 7.1 的第 2–4 步。
